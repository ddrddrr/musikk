\section{Audio Processing and Streaming}
This section describes how an uploaded audio file is turned into output
that can be streamed to the Frontend. The Streaming Protocols are
described first, since they constrain the codec and container choices
made by every later stage of the pipeline.

This section stays at the level of what each stage does and what
parameters it uses. The deeper rationale and the per-flag breakdown
of every call are in \path{text/extras/audio_processing_details.tex}.
Anything mentioned below but not explained in detail is covered there.

\subsection{Streaming Protocols}
Two protocols are used: MPEG-DASH~\parencite{dash} on devices that
support Media Source Extensions, and HLS~\parencite{hls} on iOS, which
does not support MSE\@. The basic principles behind both protocols
were covered in the \hyperref[it:streaming]{Segmented HTTP Streaming}
section.

Both protocols expect audio split into short chunks paired with a
manifest. The Packaging step is the one that produces those.

\subsection{Packaging}
Packaging cuts the transcoded audio into short fragmented MP4 segments
and generates a DASH manifest (\texttt{*.mpd}) and an HLS master
playlist (\texttt{*.m3u8}) that point at them.~\parencite{packaging_def}
The segments follow Common Media Application Format~(CMAF), so a single
set of chunks works for both protocols. The output is one
initialization segment (\texttt{*\_init.mp4}) per representation and a
sequence of media segments (\texttt{*.m4s}).

Packaging only arranges existing audio. The CLI tools that produce and
analyze that audio in the first place are introduced next.

\subsection{Processing Tools}
Three CLI tools drive the pipeline: FFmpeg~\parencite{ffmpeg} for
Transcoding and audio analysis, FFprobe (shipped with FFmpeg) for
reading source metadata, and Shaka Packager~\parencite{shaka_packager}
for the Packaging step. FFmpeg can package too, but its output had
compatibility issues with Shaka Player~\parencite{shaka_player}, used
on the Frontend for Playback, so a separate packager was chosen.

With FFmpeg in place as the encoder and analyzer, the Transcoding
configuration it runs can be described.

\subsection{Transcoding}
Transcoding decodes the source audio and re-encodes it into the target
codecs and bitrates. Raw audio formats such as WAV are too large for
Streaming, for example a 3-minute stereo 24-bit 44.1\,kHz recording is
roughly 50\,MB\@. Lossless FLAC and lossy AAC/HE-AACv2 were selected as
the output codecs, since HLS only allows a small set of audio
codecs.~\parencite{apple_hls_specs_audio} The AAC encoder used is
\texttt{libfdk\_aac}, chosen over the other AAC encoders shipped with
FFmpeg for its quality and licensing terms.

The output configuration was chosen based on existing research:~\parencite{codec_evaluation_1, codec_evaluation_2,
    codec_evaluation_3, spotify_codecs, apple_hls_specs_audio, mdn_aac}
\begin{itemize}
    \item \textbf{AAC}: 96, 160, and 320\,kbps
    \item \textbf{HE-AACv2}: 24\,kbps
    \item \textbf{FLAC}: lossless
\end{itemize}
Multiple bitrates support adaptive streaming. The AAC tiers use
Constant Bitrate~(CBR), so the Frontend's Adaptive Bitrate logic has a
stable per-tier bandwidth to pick from.

Transcoding assumes a clean, well-bounded input. The Audio
Preprocessing step described next ensures that each upload is valid
and within the proper limits, and also captures the metadata of the result.

\subsection{Audio Preprocessing}
\label{subsec:audio_preprocessing}
Before Transcoding, the upload is validated and normalized. After
Transcoding, the loudness is measured. The sub-blocks below cover
input validation, metadata extraction, the normalization filter chain,
and the loudness measurement.

\subsubsection*{Input validation}
The upload passes through a chain of checks. The file-size and MIME checks
run on the raw bytes. Other checks use values reported by FFprobe. Together
they restrict the worst-case storage and Transcoding time of a single upload:
\begin{itemize}
    \item \textbf{MIME type}, inspected with
    \texttt{python-magic}~\parencite{pythonmagic}, must be \texttt{audio/*}
    and belong to an allow-list of supported subtypes.
    \item \textbf{Codec}, reported by FFprobe, must belong to an allow-list
    of well-tested codecs.
    \item \textbf{File size}: up to 2\,GB, roughly a 2-hour 24-bit,
    48\,kHz stereo WAV\@.
    \item \textbf{Duration}: up to 7200\,s (2\,h).
    \item \textbf{Sample rate}: 1\,Hz to 384\,kHz.
    \item \textbf{Channel count}: 1 to 8.
\end{itemize}
The allow-lists are defined in \path{streaming/audio/config.py}.

\subsubsection*{Input metadata extraction}
FFprobe reads the source codec, sample rate, channel count, bit depth,
duration, and bitrate. These values are reused by the input validation
above. They also narrow which outputs the Transcoding step produces:
FLAC is skipped for lossy sources, and AAC tiers whose target
bitrate is above the source bitrate are dropped.

\subsubsection*{Normalization and loudness}
Three normalization filters run as a single FFmpeg \texttt{-af} chain
applied inside every Transcoding subprocess. A separate loudness
measurement then runs after Transcoding. The steps are:
\begin{itemize}
    \item \textbf{Channel normalization}. Sources with three or more
    channels are downmixed to stereo. Mono and stereo inputs are kept
    as-is.
    \item \textbf{Sample rate normalization}. Each source is resampled to
    the base of its rate family (44.1\,kHz or 48\,kHz). Files below
    44.1\,kHz are kept as-is. Non-family rates default to 44.1\,kHz.
    \item \textbf{Bit depth conversion}. All audio is converted to signed
    16-bit samples, since \texttt{libfdk\_aac} does not accept higher
    precision.
    \item \textbf{Loudness measurement}. After Transcoding, FFmpeg's
    \texttt{ebur128} filter produces an integrated value in Loudness Units
    relative to Full Scale~(LUFS) and a true peak in dBTP\@. The
    measurement runs on the FLAC output if it was produced, otherwise on
    the first AAC output. Both values are stored on the Song and used by
    the Frontend player to apply a consistent Playback gain.
\end{itemize}

Once Transcoding and Packaging finish, the original upload and the
intermediate transcoded MP4s are removed. Only the packaged segments,
manifests, and the loudness values stored on the Song row survive.

The Backend code that drives all of these stages is described next.

\subsection{Backend Pipeline}
The Backend code lives under
\path{src/backend/musikk/streaming/audio/} and the class layout is
shown in \path{text/diagrams/AudioClassDiagram.png}.

Pre-pipeline validation (the file-size, MIME, and FFprobe-based checks
from the previous subsection) runs in \texttt{validators.py} before any
audio subprocess is started. The pipeline itself,
\texttt{AudioProcessingPipeline} in \texttt{processing\_pipeline.py},
threads a shared \texttt{ProcessingContext} through a chain of
\texttt{Step} instances. The configured chain runs \texttt{FFmpegStep},
then \texttt{LoudnessMeasurementStep}, then \texttt{ShakaPackagerStep}.
Each \texttt{Step} is a thin orchestrator that delegates to a wrapper
object: \texttt{FFmpegStep} calls into \texttt{FFMPEGFull}, and
\texttt{ShakaPackagerStep} calls into \texttt{ShakaPackagerMPDAndM3U8}.
Each step has a \texttt{rollback} method. If a step raises, the
previously executed steps are rolled back in reverse order. The
rollback clears the per-run temporary directory and removes any output
already written to Django storage.

\texttt{FFmpegStep} runs one FFmpeg subprocess per output tier in
parallel via a \texttt{ThreadPoolExecutor} sized to the number of
selected tiers. Threads are used rather than processes because FFmpeg
itself is multi-threaded inside each subprocess, so the Python side
only waits on the subprocess to finish. A process pool would add
overhead without speeding anything up.

How this pipeline is launched as a background task, and how its status
reaches the Frontend, is covered later in the Audio Upload section.

With the Backend producing CMAF segments and both manifests in Django
storage, the Frontend only needs a player that can consume either
manifest format. That player is described next.

\section{WebSocket Communication}
This section describes the WebSocket setup, i.e., how the WS channels are created, and
how the server or the client sends/receives the WS messages.

Messages that are sent from the server to the client are internally called ``events'', while messages
from the client to the server - ``actions''.

\subsection{Backend Handling}
The Backend WS configuration can be found under the \texttt{src/backend/musikk/websockets} directory.

The \texttt{BaseConsumer} class is responsible for processing the incoming WS connection attempts:
it first validates that the User is authenticated, adds it to
a broadcast group under the \texttt{user\_*user uuid*} key,
and creates any relevant event processing classes (see further sections for more information).
In addition, it is responsible for sending the ``events'' and routing the received ``actions'' to their handlers.

A \texttt{/ws/user} endpoint is exposed and is used for connection establishment.

\subsection{Frontend Handling}
Frontend WS configuration is located in the \texttt{src/frontend/musikk/src/ws} directory.

The \texttt{WSClient} class provides methods for connection creation/closure, ``action'' dispatch, and
``event'' processing.

Since many different parts of the Frontend may want to react to the same ``events'', it also
exposes a Pub-Sub mechanism that lets other functions/components register
custom callbacks in reaction to ``events''.

In addition, a basic reconnect mechanism is added, so that the connections are not dropped
indefinitely, for example, during short network outages.
Moreover, a queue is added for outgoing ``actions'', so that they are not lost, if the client is not
able to send them at the time of creation.
All created ``actions'' are first added to the \texttt{pendingMessages} list, and only if the
connection is established and healthy are then sent to the server.

A separate \texttt{WebSocketManager} class manages the WS connection lifecycle.
It monitors the amount of open connections and provides an interface to create/delete them.
% TODO: cite devmode
It was mostly added due to the duplicate connection issues which appeared when using React in
development mode.

\section{User Management}
This section outlines the User data model and presentation layers.

The relevant Backend code is located in the \texttt{src/backend/musikk/users} directory,
the Frontend code in the \texttt{src/frontend/musikk/src/features/user} directory.

\subsection{User Data Model}
Users in the system are represented by a \texttt{BaseUser} model which holds a
discriminator \texttt{role} field that can be of two types: an ``Artist'' or a ``Base''.
%TODO: section ref
An ``Artist'' role gives the User additional permissions, such as uploading new Songs or creating Albums (see ...).

Each user is uniquely identified by their email. The \texttt{display\_name} defaults to a random
string and does not need to be unique.

Apart from basic configuration, Users can also have relations to other Users,
which are modeled by the \texttt{UserFollow} model.
The system intentially does not create a separate model for Friend relations: this is inferred
by a presence of a ``mutual follow'', i.e., two existing \texttt{UserFollow} relations where the
\texttt{from\_user} and \texttt{to\_user} foreign keys are mirrored in each model instance.

\subsection{API}
The API provides a standard set of endpoints: a \texttt{MeView} which allows the User
to retrieve or update their information, a \texttt{UserRetrieveView} that returns the non-sensitive
information about any specfic User in the system; a \texttt{FollowedView} which lets Users follow/unfollow
other Users and retrieve the Users they Follow. \texttt{FollowersView} and \texttt{FriendsView} return the
Followers of a User and their Friends respectively.

The endpoints access is gated by permissions so that, e.g., only User's Friends would be able to see their
Followers (defined in \texttt{src/backend/musikk/users/permissions.py}).

\subsection{Frontend Presentation}
On the Frontend each User has a \texttt{ProfilePage} which is used to view and edit User's
information.
When visiting another User's Profile it is possible to follow/unfollow them using a dedicated button.
The same can be done from the \texttt{UserCard} context menu.
In addition, the Profile component renders the User Feed, see ... for more details.

\texttt{UserCard}, \texttt{UserAvatar} and \texttt{UserIdentifier} components are used throughout the application
where User presentation is needed.
For example, a \texttt{UserCard} is rendered for each Author/User search result and UserIdentifier is
shown in Comment/Post headers, so that the users are easier to identify.

User's Connections (Followed/Followers/Friend) are exposed via a \texttt{UserConnectionsProvider}.
And a WS ``events'' handler is added so that the User or Connection-related updates trigger UI re-renders.

%%\subsection{Device Handling}\label{subsec:fedevices}
%%User device management was one of the most challenging parts.
%%
%%The expected behaviour from the application would be to register a new device when
%%the User logs in, then show the list of devices on
%%which the service is running, and when a new device is chosen, switch the playback to it.
%%When the application is closed, the device should be removed from the list of active devices.
%%
%%The registration and switching part is not complicated -- it is possible to send
%%a device registration request on the first render of the \texttt{App} component,
%%which is mounted only once. The result of this request,
%%containing the device's unique identifier, then would be added to the \textit{LocalStorage}.
%%Then, on page refresh, the presence of this variable could be checked, and additional requests
%%could be omitted.

%%page or window close~\parencite{chromelfapi,beacons}.

%%which signal page refresh, redirection, or closure,
%%are inconsistent -- particularly on mobile platforms and Safari.

%%Chrome documentation recommends using the \texttt{visibilitychange} event to detect when
%%a page becomes hidden. While this event is more

%%playback device should be deactivated or removed.
%%
%%
%%Even implementing heartbeats -- periodic requests to the Backend
%%indicating that the device is still in use -— would require additional Backend
