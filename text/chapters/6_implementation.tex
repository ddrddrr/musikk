\section{Audio Processing and Streaming}
This section provides the core principles of Audio Processing and Streaming.

As was stated in the \chapterref{ch:planning} Segmented HTTP Streaming is going to be
used as the main method of audio presentation; therefore the Streaming Protocols are discussed first.
Then, the stages that are needed to make an audio file streamable are described: Transcoding and Packaging.
These stages are presented in the reverse order, as Packaging sets requirements that affect Transcoding.
In the end of the section, the software tools used for those processing steps are selected.

\subsection{Streaming Protocols}
Two protocols were chosen for audio streaming: MPEG-DASH\parencite{dash} and HLS\parencite{hls}.
The basic pricnipals behind them were
introduced in the \hyperref[it:streaming]{Segmented HTTP Streaming} section.

At first, only DASH was considered, because it works better in varying network conditions~\parencite{hls_vs_dash},
and is not limited to only a select amount of audio codecs.~\parencite{dash_technical}

% todo links to all players?
However, DASH support in audio players is typically implemented
via browser Media Source Extensions\parencite{mse}, which iOS does not support.\parencite{msecaniuse}
Since iOS accounts for roughly 15\% of all operating systems
worldwide~\parencite{os_percentage}, HLS support had to be added as well.

Both streaming protocols will therefore be used: DASH on devices that support MSE, and HLS on iOS\@.

With the protocols selected, the audio representation that is required for protocols to work is discussed next.

\subsection{Packaging}
Packaging is the step where the encoded audio is prepared for Streaming.~\parencite{packaging_def}
It mainly includes dividing the audio into chunks and generating manifest files
that reference them~(an \texttt{*.mpd} file for DASH and \texttt{*.m3u8} files for HLS).

Because the platform serves both DASH and HLS, it is useful to generate only one set of chunks and reuse it
for both streaming methods.
For this reason, the packaged output follows Common Media Application Format~(CMAF), \footnote{
    This is usually not implied strictly by packager utilities, but can be observer by running, e.g.,
    `ffprobe` CLI utility on the converted file.
}
which defines a common way to store chunks as fragmented MP4~(fMP4) containers.~\parencite{cmaf}

The resulting output would contain one initialization segment (\texttt{*\_init.mp4}), which stores audio metadata
and decoder setup, and a sequence of media segments (\texttt{*.m4s}),
which store the audio data in short time intervals.
In addition, this approach is required for streaming FLAC
encoded (lossless) audio via HLS.~\parencite{apple_hls_specs_flac_container}

But before the audio is packaged, it needs to be converted to different formats in order to support bitrate
switching.
The next subsection discusses this process, which is called Transcoding.

\subsection{Transcoding}
Transcoding is the process of decoding audio data and re-encoding it,
typically to a different codec (see explanation below) and/or different encoding settings: bitrate, sample rate, channels, etc.

Usually, when high-quality audio is recorded, it is initially saved in raw audio formats, such as WAV,
which results in big file sizes which are impractical for Streaming\@.\footnote{
    For instance, the resulting WAV file for a 3-minute stereo audio
    recording with a bit depth of 24 bits and a sample rate of 41khz is approximately 50 MB\@.
}
To reduce the size, the audio is usually processed using a special program called a \textit{codec},
which compresses and stores audio in a more efficient format.

Lossless codecs, such as FLAC~\parencite{flac_xiph}, keep all audio information, so the audio sounds exactly
the same as the original raw data.
In contrast, lossy codecs~(MP3~\parencite{mp3}, AAC~\parencite{aac}, OPUS~\parencite{opus}, etc.)
remove some information to reduce file size, which can slightly reduce quality, especially at low bitrates.

In this implementation, the lossless FLAC codec and lossy AAC and HE-AAC codecs were selected due to their
good performance in web-based streaming scenarios.~\parencite{codec_evaluation_1, codec_evaluation_2, codec_evaluation_3}:
Other codecs that theoretically promise to provide better sound quality at smaller file sizes,
such as Opus or MP3, were also researched; however, for higher bitrates that are used in Streaming they did not
provide any advantage.
Moreover, only *-AAC and FLAC codecs are supported for HLS streaming.~\parencite{apple_hls_specs_audio}

Codecs usually provide several parameters that affect the output, such as sample rate, the number
of channels, and bitrate.
Bitrate describes how much audio data is stored or transmitted per second and is typically expressed in KB/s\@.
It is commonly used because it provides a direct way to control the trade-off between audio
quality and file size.

Before selecting the encoding configuration, it is also important to distinguish
between two encoding strategies: Constant Bitrate~(CBR)~\parencite{cbr}
and Variable Bitrate~(VBR).~\parencite{vbr}

CBR keeps the bitrate fixed across the entire audio file, resulting in predictable chunk
sizes and smooth playback during Streaming.
VBR adjusts the bitrate depending on content complexity,
which can provide better quality at a smaller size compared to CBR,
but can lead to inconsistent segment sizes, making Streaming less stable~\parencite{cbrvbrcomp}.
% TODO: this is not the reason no, cbr was chosen because we can have multiple representations
% what if vbr is still too big for some conditions?
% or multi-vbr also exists...
For this reason, a \textbf{multi-CBR setup} was selected.
While less efficient in terms of quality-to-size ratio compared to VBR,
CBR provides better predictability when Streaming.

The following configuration was chosen based on the available
research and recommendations~\parencite{codec_evaluation_1, codec_evaluation_2,
    codec_evaluation_3, spotify_codecs, apple_hls_specs_audio, mdn_aac}:
\begin{itemize}
    \item \textbf{AAC}: 96, 160, and 320 kbps
    \item \textbf{AAC-HEv2}: 24 kbps
    \item \textbf{FLAC}: lossless
\end{itemize}
As mentioned before, multiple bitrates are included in order to support adaptive streaming.

The tools which are used to do the Packaging and Transcoding are introduced next.

\subsection{Processing Tools}
Transcoding is done via \texttt{ffmpeg}~\parencite{ffmpeg}, which is an open-source CLI tool.
It is used because it offers support for all of the selected codecs, can be run programmatically as a script
and provides high speed of audio conversion, since it is written in C and is optimized to use multiple threads.
%TODO: improve
\texttt{ffmpeg} provides multiple codec implementations, out of which \texttt{libfdk\_aac} and \texttt{flac} were used.
While there is only one codec for FLAC, \texttt{ffmpeg} has three for AAC:
\begin{itemize}
    \item \texttt{aac_at} - the best available codec in terms of quality.~\parencite{aac_codec_cmp_1,aac_codec_cmp_2,aac_codec_cmp_3}
    However, it was excluded due to its licencing policy which states that this codec could be used only on Apple-branded devices.\parencite{aac_at_licensing,ffmpeg_aac}
    \item \texttt{aac} - the \texttt{ffmpeg}'s own AAC codec implementation.
    It was also rejected, since the quality it provides is sub-par (even stated by the official documentation),
    lacking behing the other two codecs.~\parencite{aac_codec_cmp_1,aac_codec_cmp_2,aac_codec_cmp_3, ffmpeg_aac}
    \item \texttt{libfdk_aac} - the second best codec in terms of quality and the codec that was eventually chosen.
    Although, it also has licencing issues, notably any binaries, Docker images and other distribution methods which
    use it can not be made public or freely shipped to other devices, it is available for use
    free of charge in closed-source projects.~\parencite{vialicensing_aac, spdx_aac, ffmpeg_aac}
\end{itemize}

The resulting \texttt{ffmpeg} command that is used for Transcoding looks like this:
% TODO: make on same page
\begin{minted}{bash}
ffmpeg -i *input file path*
    -vn -sn -dn
    -c:a *encoder* *encoder extras*
    -b:a *bitrate*
    -movflags
    +faststart
    *resulting file path*
\end{minted}

Where individual flags are:
\begin{itemize}
    \item \texttt{-i *input file path*} selects the input media file.
    \item \texttt{-vn} disables video streams.
    \item \texttt{-sn} disables subtitle streams.
    \item \texttt{-dn} disables data streams.
    \item \texttt{-c:a *encoder*} selects the audio encoder/codec used for the output~(e.g., \texttt{flac}, \texttt{libfdk\_aac}).
    \item *encoder extras* are additional encoder-specific options~(e.g., \texttt{-profile aac\_he\_v2} for \texttt{libfdk\_aac}).
    \item \texttt{-b:a *bitrate*} sets the target audio bitrate~(e.g., \texttt{96k}).
    \item \texttt{-movflags +faststart} moves the MP4 metadata~(\texttt{moov} atom~\parencite{moov})
    to the beginning of the file to improve download/streaming startup.
    \item \texttt{*resulting file path*} sets the output file path.
\end{itemize}

Even though \texttt{ffmpeg} is able to do the Packaging step as well, a dedicated packager tool was decided to be used.
This is due to the problems that \texttt{ffmpeg} had with generating manifests which are
% todo link to frontend
% todo say about problems that were there?
compatible with Shaka Player~\parencite{shaka_player}~(that is used on the Frontend for audio playback, see Frontend section for details)
As a consequence, Shaka Packager was selected for the packaging step.~\parencite{shaka_packager}
It supports both DASH and HLS, can generate CMAF-style fMP4 segments, and can produce both manifests in one run.
In addition, it integrates well with Shaka Player.

The resulting Shaka Packager command that is used for Packaging looks like this:
\begin{minted}{bash}
packager
  "input=*file path 1*,stream=audio,
   init_segment=*base path*/audio_0_init.mp4,
   segment_template=*base path*/audio_0_$Number$.m4s,
   playlist_name=audio_0.m3u8"
  "input=*file path 2*,stream=audio,
   init_segment=*base path*/audio_1_init.mp4,
   segment_template=*base path*/audio_1_$Number$.m4s,
   playlist_name=audio_1.m3u8"
  ...
  --segment_duration 3
  --generate_static_live_mpd
  --mpd_output=*base path*/manifest.mpd
  --hls_master_playlist_output=*base path*/master.m3u8
\end{minted}

Where individual flags are:
\begin{itemize}
    \item \texttt{packager} -- the Shaka Packager binary.
    \item \texttt{"input=*file path N*,stream=audio,init\_segment=*path*,
        segment\_template=*path*,playlist\_name=*name*"} defines one packaging input, where:
    \begin{itemize}
        \item \texttt{input=*path*} is the local path to the downloaded source audio file.
        \item \texttt{stream=audio} selects the audio stream from the file for packaging.
        \item \texttt{init\_segment=*path*} sets the output path for the CMAF/fMP4 initialization segment~(\texttt{*\_init.mp4}).
        \item \texttt{segment\_template=*path*} sets the template for media segment file names.
        \item \texttt{playlist\_name=*name*} sets the name of the per-representation HLS media playlist~(variant playlist), e.g., \texttt{audio\_0.m3u8}.
    \end{itemize}
    \item \texttt{--segment\_duration 3} sets the target segment duration in seconds.
    \item \texttt{--generate\_static\_live\_mpd} generates a static MPD with, which is used for better compatibility with audio players.
    \item \texttt{--mpd\_output=*path*} sets the output path for the DASH manifest~(\texttt{manifest.mpd}).
    \item \texttt{--hls\_master\_playlist\_output=*path*} sets the output path for the HLS master playlist~(\texttt{master.m3u8}).
\end{itemize}

\section{WebSocket Communication}
This section describes the WebSocket setup, i.e., how the WS channels are created, and
how the server or the client sends/receives the WS messages.

Messages that are sent from the server to the client are internally called ``events'', while messages
from the client to the server -- ``actions''.

\subsection{Backend Handling}
The Backend WS configuration can be found under the \texttt{src/backend/musikk/websockets} directory.

The \texttt{BaseConsumer} class is responsible for processing the incoming WS connection attempts:
it first validates that the User is authenticated, adds it to
a broadcast group under the \texttt{user\_*user uuid*} key,
and creates any relevant event processing classes (see further sections for more information).
In addition, it is responsible for sending the ``events'' and routing the received ``actions'' to their handlers.

A \texttt{/ws/user} endpoint is exposed and must be used for connection establishment.

\subsection{Frontend Handling}
Frontend WS configuration is located in the \texttt{src/frontend/musikk/src/ws} directory.

The \texttt{WSClient} class provides methods for connection creation/closure, ``action'' dispatch, and
``event'' processing.

Since many different parts of the Frontend may want to react to the same ``events'', it also
exposes a Pub-Sub mechanism that lets other functions/components register
custom callbacks in reaction to ``events''.

In addition, a basic reconnect mechanism is added, so that the connections are not dropped
indefinitely, for example, during short network outages.
Moreover, a queue is added for outgoing ``actions'', so that they are not lost, if the client is not
able to send them at the time of creation.
All created ``actions'' are first added to the \texttt{pendingMessages} list, and only if the
connection is established and healthy are then sent to the server.

A separate \texttt{WebSocketManager} class manages the WS connection lifecycle.
It monitors the amount of open connections and provides an interface to create/delete them.
% TODO: cite devmode
It was mostly added due to the duplicate connection issues which appeared when using React in
development mode.

\section{User Management}
This section outlines the User data model and presentation layers.

The relevant Backend code is located in the \texttt{src/backend/musikk/users} directory,
the Frontend code in the \texttt{src/frontend/musikk/src/features/user} directory.

\subsection{User Data Model}
Users in the system are represented by a \texttt{BaseUser} model which holds a
discriminator \texttt{role} field that can be of two types: an ``Artist'' or a ``Base''.
%TODO: section ref
An ``Artist'' role gives the User additional permissions, such as uploading new Songs or creating Albums (see ...).
Currently there are no additional properties that the Artist need to have, however, in the future this design
could be extended, for example, with a new ArtistProfile model that would
include additional information, such as upcoming Artist events or revenue data.

Each user is uniquely identified by their email; display_name defaults to a random
string and does not need to be unique.

Apart from basic configuration, Users can also have relations to other Users,
which is modeled by the \texttt{UserFollow} model.
The system intentially does not create a separate model for Friend relations: this is inferred
by a presence of a ``mutual follow'', i.e., two existing \texttt{UserFollow} relations where the
\texttt{from_user} and \texttt{to_user} foreign keys are mirrored in each model instance.

\subsection{API}
The API provides a standard set of endpoints: a \texttt{MeView} which allows the User
to retrieve or update their information; a \texttt{UserRetrieveView} that returns the non-sensitive
information about any specfic User in the system; a \texttt{FollowedView} which lets Users follow/unfollow
other Users and retrieve the Users they Follow. \texttt{FollowersView} and \texttt{FriendsView} return the
Followers of a User and their Friends respectively.

The endpoints access is gated by permissions so that, e.g., only User's Friends would be able to see their
Followers (defined in \texttt{src/backend/musikk/users/permissions.py}).

\subsection{Frontend Presentation}
On the Frontend each User has a \texttt{ProfilePage} which is used to view and edit User's
information.
When visiting another User's Profile it is possible to follow/unfollow them using a dedicated button.
The same can be done from the \texttt{UserCard} context menu.
In addition, the Profile component renders the User Feed, see ... for more details.

\texttt{UserCard}, \texttt{UserAvatar} and \texttt{UserIdentifier} components are used throughout the application
where User presentation is needed.
For example, a \texttt{UserCard} is rendered for each Author/User search result and UserIdentifier is
shown in Comment/Post headers, so that the users are easier to identify.

User's Connections (Followed/Followers/Friend) are exposed via a \texttt{UserConnectionsProvider}.
And a WS ``events'' handler is added so that the User or Connection-related updates trigger UI re-renders.

%%The component hierarchy is decomposed into several levels:
%%
%%\begin{itemize}
%%    \item \textbf{Groupings and Logic Providers} – High-level wrappers that provide context,
%%    routing or shared state to nested components, for example \texttt{App} or \texttt{HomePage}.
%%    \item \textbf{Layout Components} – Define page structure and positioning
%%    (e.g., \texttt{Header}, \texttt{RightColumn}, \texttt{PlayerBox}).
%%    \item \textbf{Data Representation Components} – Render fetched data and define interactions on it.
%%    \item \textbf{UI Subcomponents} – Reusable elements like buttons,
%%    inputs, and fields used across higher-level components.
%%\end{itemize}
%%
