\chapter{Audio Processing Pipeline Details}\label{app:audio_details}
These notes expand on the \textit{Audio Processing and Streaming}
section of \chapterref{ch:implementation}. The main chapter names every
stage briefly and lists the chosen parameters. The sections below give
the fuller reasoning for each choice and a per-flag breakdown of every
CLI command.

\section{Streaming Protocols}
DASH was considered first, because it works better in varying network
conditions~\parencite{hls_vs_dash} and is not limited to a small set
of audio codecs.~\parencite{dash_technical} However, DASH support in
audio players is usually built on top of browser Media Source
Extensions~\parencite{mse}, which iOS does not
support.~\parencite{msecaniuse} Since iOS makes up about 15\% of all
operating systems worldwide~\parencite{os_percentage}, HLS support had
to be added as well.

\section{Packaging}
Two notes on CMAF packaging. First, packager tools rarely state in
their output that the segments follow CMAF\@. This can be checked by
running, for example, the \texttt{ffprobe} CLI tool on a packaged
segment. Second, the resulting output is split into one initialization
segment (\texttt{*\_init.mp4}), which stores audio metadata and
decoder setup, and a sequence of media segments (\texttt{*.m4s}),
which store the audio data in short time intervals.

In addition, fMP4 segments are required for streaming FLAC encoded
(lossless) audio via HLS\@.~\parencite{apple_hls_specs_flac_container}

\section{Processing Tools}
Three CLI tools are used in the processing pipeline: FFmpeg for
Transcoding and audio analysis, FFprobe for reading audio metadata,
and Shaka Packager for the Packaging step.

FFmpeg supports all of the selected codecs, can be run from a script,
and converts audio at high speed because it is written in C and uses
multiple threads. The pipeline uses it both as the transcoder and as
the host for the filter chain applied during Audio Preprocessing.

FFprobe comes with the FFmpeg project and reads metadata from audio
files. The Audio Preprocessing pipeline uses it to read the source
codec, sample rate, channel count, bit depth, duration, and bitrate of
every upload before Transcoding.

\section{Transcoding}
\subsection{AAC encoder choice}
FFmpeg comes with several AAC encoder implementations, only one of
which is used here:
\begin{itemize}
    \item \texttt{aac\_at} is the best codec in terms of
    quality.~\parencite{aac_codec_cmp_1,aac_codec_cmp_2,aac_codec_cmp_3}
    However, it was not chosen because its license only allows use on
    Apple-branded devices.~\parencite{aac_at_licensing,ffmpeg_aac}
    \item \texttt{aac} is FFmpeg's own AAC implementation. It was
    also rejected, since the quality it gives is worse than the other
    two codecs listed here (this is even stated in the official
    documentation).~\parencite{aac_codec_cmp_1,aac_codec_cmp_2,aac_codec_cmp_3,ffmpeg_aac}
    \item \texttt{libfdk\_aac} is the second best codec in terms of
    quality and the one that was chosen. It also has license limits:
    any binaries, Docker images, and other distribution methods that
    include it cannot be made public or freely sent to other devices.
    However, it can be used free of charge in closed-source
    projects.~\parencite{vialicensing_aac,spdx_aac,ffmpeg_aac}
\end{itemize}
For FLAC, FFmpeg provides a single \texttt{flac} encoder, which is
used directly.~\parencite{ffmpeg_flac}

\subsection{Bitrate strategy: CBR versus VBR}
Bitrate describes how much audio data is stored or sent per second.
It is usually given in kilobits per second (kbps) and is the main way
to balance audio quality against file size.

Two encoding strategies exist: Constant
Bitrate~(CBR)~\parencite{cbr} and Variable
Bitrate~(VBR).~\parencite{vbr} CBR keeps the bitrate fixed across
the entire audio file, so each representation has a known, stable
bandwidth. VBR changes the bitrate based on content complexity, which
gives better quality at a smaller size compared to CBR, but the
per-segment size varies within a single
representation.~\parencite{cbrvbrcomp}

A multi-CBR setup was chosen because the Frontend's Adaptive Bitrate
logic needs a stable per-tier bandwidth to pick from. The same effect
could in principle be reached with constrained VBR tiers, but the
fixed per-tier bitrate is simpler for the project scope.

\subsection{Generation loss}
Transcoding a lossy source into AAC causes generation loss~\parencite{generation_loss}. Every
lossy pass throws away some audio, so re-encoding what was already
lossy makes the loss worse. The pipeline still does the conversion
because DASH and HLS need every representation in the same codec.
With FLAC and AAC chosen as the output codecs, lossy uploads have to
be re-encoded into AAC anyway.

\section{Audio Preprocessing}
\subsection{Input validation limits}
The upload passes through a chain of validation checks. The
file-size and MIME checks run on the raw bytes. The remaining checks
read values from the file with FFprobe. Raw audio storage grows
linearly with duration, sample rate, channel count, and bit depth,
so the limits together cap the worst-case storage and Transcoding
time of a single upload:
\begin{itemize}
    \item \textbf{MIME type}. The first 2048 bytes of the file are
    inspected with \texttt{python-magic}~\parencite{pythonmagic}, and
    the type must start with \texttt{audio/}. The subtype must also
    belong to an allow-list of subtypes that map to the supported
    codecs, defined in the \texttt{ALLOWED\_FILE\_TYPES} variable in
    \texttt{streaming/audio/config.py}. This step catches malformed
    or non-audio uploads before any audio tool is started.
    \item \textbf{Codec allow-list}. A container can hold different
    codecs (for example, an \texttt{.mp4} file can hold AAC or
    ALAC), so the codec name FFprobe reports must also belong to
    \texttt{ALLOWED\_CODECS} in \texttt{streaming/audio/config.py}.
    The list only covers popular codecs.
    \item \textbf{File size: 2\,GB}. Roughly a 2-hour 24-bit,
    48\,kHz stereo WAV\@. An arbitrary number, but real music files
    usually stay well below this, so the limit mostly guards against
    accidental or malicious oversize uploads.
    \item \textbf{Duration: up to 7200\,s (2\,h)}. Covers DJ sets
    and long mixes while keeping the upload and Transcoding time
    reasonable.
    \item \textbf{Sample rate: 1\,Hz to 384\,kHz}. The upper bound
    matches the highest rate in the supported sample rate families,
    described in the Sample rate normalization step below.
    \item \textbf{Channel count: 1 to 8}. Covers mono through 7.1
    surround, which is the practical upper bound for source audio.
\end{itemize}

\subsection{FFprobe invocation}
\begin{minted}{bash}
ffprobe -v error -select_streams a \
    -show_entries stream=codec_name,sample_rate,channels,bits_per_raw_sample,duration,bit_rate \
    -show_entries format=duration,bit_rate \
    -of json input.wav
\end{minted}

The flags are:
\begin{itemize}
    \item \texttt{-v error} hides informational and warning output
    and keeps only actual errors.
    \item \texttt{-select\_streams a} limits probing to audio
    streams.
    \item \texttt{-show\_entries stream=...} returns only the
    per-stream fields the wrapper uses.
    \item \texttt{-show\_entries format=...} adds a fallback for
    \texttt{duration} and \texttt{bit\_rate}, since some containers
    (notably WAV) only report them at the format level.
    \item \texttt{-of json} produces structured output that the
    wrapper parses.
\end{itemize}

\subsection{Channel normalization}
The normalization step reduces every track to mono or stereo. Music
releases are mostly mastered in stereo, and the chosen Streaming
Protocols and the loudness measurement step below are also defined
for mono or stereo input. Surround formats such as Dolby Atmos~\parencite{dolby_atmos} need
a different container, extra information in the manifest, and
per-platform decoder support, none of which fit the project scope.~\parencite{itu_bs775}

Mono inputs stay mono, since upmixing to stereo would not add
information, only file size. Stereo inputs stay stereo. Sources with
three or more channels are downmixed to stereo by adding
\texttt{aresample=out\_chlayout=stereo} to the FFmpeg filter chain.

\subsection{Sample rate normalization}
Human hearing tops out around 20\,kHz. The Nyquist-Shannon theorem~\parencite{shannon_sampling}
says a sample rate must be at least twice the highest frequency in
the signal to represent it without aliasing. A 44.1\,kHz rate
therefore covers the audible band with a small margin, and source
rates above that give no extra audio quality, only larger files.~\parencite{lavry_sample_rate}

Music masters use one of two standard rates, 44.1\,kHz or 48\,kHz~\parencite{aes5},
or an integer multiple of one of them. The step groups each source
into its family and resamples down to the family base. An
integer-ratio resample is fast to compute and stays close to the
original signal. Files below 44.1\,kHz are left as they are, since
upsampling adds no information. Non-family rates default to
44.1\,kHz. Resampling is done by adding \texttt{aresample=<rate>}
to the FFmpeg filter chain.

\subsection{Bit depth conversion}
All audio is converted to signed 16-bit samples through
\texttt{aformat=sample\_fmts=s16}. The conversion is always applied,
because \texttt{libfdk\_aac}, the encoder used for the AAC tiers,
does not accept higher-precision sample formats. FLAC accepts higher
precision, but using the same filter chain for every tier keeps the
Transcoding command the same across tiers.

\subsection{Loudness theory}
Loudness normalization keeps the perceived volume steady across
tracks~\parencite{audio_normalization}. Human hearing is not flat: equal-loudness contours described
by ISO~226~\parencite{iso226} show that perceived loudness depends on both amplitude
and frequency, so two files with the same digital peak can sound
very different. Without normalization, a playlist that mixes tracks
from different masters would have the listener constantly reaching
for the volume knob.

ITU-R BS.1770~\parencite{itu_bs1770} is the standard algorithm for measuring loudness. It
produces an integrated value in Loudness Units relative to Full
Scale~(LUFS), using a frequency weighting (K-weighting) made to
match how humans hear and a channel weighting model. EBU R128~\parencite{ebu_r128} turns
the algorithm into a normalization recommendation, with a broadcast
target of \(-23\)\,LUFS\@. Streaming services use higher targets
because listening conditions differ from broadcast, for example
Spotify at \(-14\)\,LUFS~\parencite{spotify_loudness} and Apple Music at \(-16\)\,LUFS\@.~\parencite{apple_music_loudness}

Two other units appear here. Decibels Full Scale~(dBFS) measure
sample amplitude relative to the largest value the format can store,
so 0\,dBFS is the largest sample and recorded peaks are usually
negative. True peak in dBFS~(dBTP) measures the peak of the
reconstructed analog waveform after digital-to-analog conversion,
not the peak of the stored samples. The difference matters: a
sequence of samples that are all below 0\,dBFS can still reconstruct
to over 0\,dBFS, producing inter-sample peaks that clip on Playback.
True-peak measurement uses an oversampled signal to catch this.

\subsection{Why loudness is measured after Transcoding}
FFmpeg's \texttt{ebur128} filter with \texttt{peak=true} produces
both an integrated LUFS value and a true peak in dBTP. The
measurement runs after Transcoding, on the FLAC output if it was
produced, otherwise on the first AAC output. FLAC is preferred when
available because it keeps the normalized signal bit-perfectly. The
measured values therefore describe the normalization output without
being changed by the lossy AAC encoder.

The measurement happens after Transcoding rather than on the source
file for two reasons. First, the listener hears the audio after
processing. Channel downmix changes overall loudness, since each
channel adds to the perceived sum. Sample-rate conversion can also
shift true peaks slightly. The stored values therefore have to
describe what actually plays. Second, the \texttt{ebur128} summary
reports the peak as a per-channel list on multichannel inputs. For
example, a six-channel source produces a summary line such as
\texttt{Peak: -1.1 -2.3 -1.5 -2.1 -3.0 -1.8 dBFS}, which is unclear
as a single per-track value. After downmix to stereo the list has
at most two entries, and the wrapper records the maximum of the two.

\section{Pipeline invocations}
\subsection{FFmpeg transcoding flags}
The FFmpeg command for the AAC 160\,kbps tier on a stereo 44.1\,kHz
source is:
\begin{minted}{bash}
ffmpeg -i input.wav \
    -vn -sn -dn \
    -af "aresample=out_chlayout=stereo,aresample=44100,aformat=sample_fmts=s16" \
    -c:a libfdk_aac \
    -b:a 160k \
    -movflags +faststart \
    libfdk_aac-160-<uuid>.mp4
\end{minted}

The flags are:
\begin{itemize}
    \item \texttt{-i input.wav} selects the input media file.
    \item \texttt{-vn -sn -dn} strip any video, subtitle, and data
    streams, so only the audio stream is processed.
    \item \texttt{-af "..."} applies the audio filter chain for
    normalization (channel downmix, sample-rate normalization,
    bit-depth conversion).
    \item \texttt{-c:a libfdk\_aac} selects the audio encoder. The
    other encoders used by the pipeline are \texttt{flac} for the
    lossless tier and \texttt{libfdk\_aac} with the extra
    \texttt{-profile aac\_he\_v2} flag for the HE-AACv2 24\,kbps
    tier.
    \item \texttt{-b:a 160k} sets the target audio bitrate. This
    flag is left out for the FLAC tier, since it is lossless.
    \item \texttt{-movflags +faststart} moves the MP4 metadata (the
    \texttt{moov} atom~\parencite{moov}) to the start of the file,
    so Playback can begin before the whole file is downloaded.
    \item The last positional argument is the output file path.
    The wrapper uses the pattern
    \texttt{<encoder>-<bitrate>-<uuid>.mp4} for the lossy tiers and
    \texttt{flac-static-<uuid>.mp4} for the lossless tier.
\end{itemize}

\subsection{Shaka Packager flags}
The Shaka Packager command for two of the AAC tiers is:
\begin{minted}{bash}
packager \
  'input=/tmp/in/libfdk_aac-96-<uuid>.mp4,stream=audio,init_segment=/tmp/out/audio_0_init.mp4,segment_template=/tmp/out/audio_0_$Number$.m4s,playlist_name=audio_0.m3u8' \
  'input=/tmp/in/libfdk_aac-160-<uuid>.mp4,stream=audio,init_segment=/tmp/out/audio_1_init.mp4,segment_template=/tmp/out/audio_1_$Number$.m4s,playlist_name=audio_1.m3u8' \
  --segment_duration 3 \
  --generate_static_live_mpd \
  --mpd_output=/tmp/out/manifest.mpd \
  --hls_master_playlist_output=/tmp/out/master.m3u8
\end{minted}

The Backend builds this command as a Python list and runs it through
\texttt{subprocess}, without a shell, so the \texttt{\$Number\$}
token is passed to the packager as-is. The example above wraps each
per-input argument in single quotes so that bash does not expand
the token.

The flags are:
\begin{itemize}
    \item \texttt{packager} is the Shaka Packager binary.
    \item Each \texttt{input=...} argument defines one
    representation. The keys are:
    \begin{itemize}
        \item \texttt{input=<path>} is the local path to the
        transcoded audio file.
        \item \texttt{stream=audio} selects only the audio stream
        from that file.
        \item \texttt{init\_segment=<path>} sets the output path
        for the CMAF/fMP4 initialization segment
        (\texttt{*\_init.mp4}).
        \item \texttt{segment\_template=<path>} sets the template
        for media segment file names. \texttt{\$Number\$} is a
        placeholder that the packager replaces with the segment
        index.
        \item \texttt{playlist\_name=<name>} sets the file name of
        the per-representation HLS variant playlist, for example
        \texttt{audio\_0.m3u8}.
    \end{itemize}
    \item \texttt{--segment\_duration 3} sets the target segment
    length in seconds. The value of 3\,s was chosen as a balance
    between how fast the player can switch bitrates and the cost
    of each HTTP request.
    \item \texttt{--generate\_static\_live\_mpd} switches the DASH
    manifest type from \texttt{dynamic} (the default) to
    \texttt{static}, which is what audio-on-demand clients expect
    and which lets the player seek through the track.
    \item \texttt{--mpd\_output=<path>} sets the output path for
    the DASH manifest (\texttt{manifest.mpd}).
    \item \texttt{--hls\_master\_playlist\_output=<path>} sets the
    output path for the HLS master playlist (\texttt{master.m3u8}).
\end{itemize}

\subsection{ebur128 loudness measurement flags}
The FFmpeg command for the loudness pass, run on the FLAC output
if it was produced or otherwise on the first AAC output, is:
\begin{minted}{bash}
ffmpeg -i flac-static-<uuid>.mp4 \
    -filter:a ebur128=peak=true \
    -f null -
\end{minted}

The flags are:
\begin{itemize}
    \item \texttt{-i <path>} selects the transcoded audio file the
    wrapper picked for measurement.
    \item \texttt{-filter:a ebur128=peak=true} runs the
    \texttt{ebur128} audio filter. \texttt{peak=true} turns on
    true-peak measurement (dBTP) alongside the integrated LUFS
    value, so the wrapper gets both numbers from a single pass.
    \item \texttt{-f null -} discards the audio output, since only
    the summary the filter prints on stderr is needed. The
    trailing \texttt{-} tells FFmpeg to write the (discarded)
    output to stdout.
\end{itemize}

The wrapper parses the printed summary, extracts the \texttt{I:}
(LUFS) and \texttt{Peak:} (dBTP) values, and stores them on the
Song row.
